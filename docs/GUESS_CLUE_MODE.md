# 猜人物：线索模式

线索玩法使用历史通识，不受本站史料录入范围限制。书法、诗词、作品、成就与典故都可以出题。本站资料是可选背景，不能把资料缺失理解为人物不出名或事迹不存在。

## 数据与身份

- `guess_character` 保存稳定的游戏人物 UUID、姓名/别称、年代信息和出题状态。`canonical_person_id` 可为空，已有本站人物则显式绑定；同名不自动合并。没有本站人物页时，揭晓不显示空链接。
- 原题库的身份通过迁移/准备命令同步到游戏人物表；线索模式以原题库难度作为初始分档，此后独立保存评价和分档，避免“问题难问”与“线索难猜”互相干扰。人物身份仍然复用。
- 尚未录入的知名人物也可以新增为游戏人物，不向 `person`、`fact_claim`、`source` 或录入账本写入通识信息。以后录入了对应人物，应核对身份后显式绑定，不能按姓名自动关联。
- `guess_clue_set` 按游戏人物、人物资料指纹和生成版本保存完整六条线索、揭晓解释、准备状态、租约、时间戳及 provenance。通识线索不伪装成本站原文引文。
- 两种玩法共用 `guess_character` 目录。提问模式可读取已准备线索的解释作为通识资料卡，未录入史料的人物也可开局；已有原文仍保留为额外依据。没有依据时回答“不清楚”，不凭模型记忆编造。通识条目标为 `general_knowledge`，使用游戏资料 ID，不伪装成原文 claim。
- 提问模式原有人物继续使用 `guess_bank` 和原有评价；新增游戏人物的提问评价保存在 `guess_question_feedback`，线索评价保存在 `guess_clue_feedback`。人物没有分库，玩法统计各自记录。

`period_from` / `period_to` 是玩法的朝代归属范围，用于筛选，不能当作人物生卒年；未知生卒年继续保留为空。

## 难度反馈

揭晓后，猜过名字或至少打开过下一条线索的玩家，可以评价“太简单了／刚刚好／太难了”。结果保存到 `guess_clue_feedback`，重复提交同一局或同一匿名玩家对同套线索同一分档轮次的评价只计一次。题目、已看线索数、猜测次数与结果一并保留，便于后续分析。

至少 12 份有效评价，且至少 75% 认为应该调到另一档，才会在简单／困难之间切换。旧轮次评价留档但不影响新轮次；内容更新后的评价重新累计。规则与提问模式共用，统计独立。重新导入人物资料不能覆盖玩家已调整的分档。

本地预览也会把评价保存在文件中，正式服务由 MySQL 事务保存，并用人物行锁保护并发去重与计数。

## 准备与复用

`games/guess/starter-clues.json` 当前包含 168 位已准备人物：159 位简单人物、9 位困难样例，共 1,008 条线索。已覆盖 2026-10-20 核对的原提问题库全部 119 位简单人物；身份清单与覆盖日期保存在 `preparation-manifest.json`。`characters.json` 中 121 位显式绑定本站人物，47 位使用游戏身份。初始分档与原题库对齐，之后各玩法反馈分别调整。

168 是已准备线索的人数，不是共用人物库的容量。完整人物目录由 MySQL 中的原 `guess_bank` 与游戏新增人物共同形成，不用这个题包替换原库。两种模式及批量准备程序共用 `GuessCharacterCatalogue` 同步目录；先进入线索模式也会完成同一次同步，新增史料人物不会依赖先玩一次提问模式才能进入目录。同步只新增身份，不覆盖任一玩法已经调整的难度。

普通简单开局仅抽取准备好的题目，不调用模型。困难人物首次抽到时生成整套六条线索，保存后重用；点击“下一条”只解锁缓存内容。生成进程使用跨实例数据库租约和进程内 single-flight；一个浏览器断开不会取消其他人共用的准备。生成失败进入短暂冷却，不缓存无效题。困难开局只尝试一个新目标；资料不足或等待超过 45 秒时，优先退回同难度、同年代中已准备的人物，共用准备仍可在后台完成，避免一次开局连调多个模型。没有可用的可靠线索时明确报错。新增游戏人物在困难提问模式缺少资料卡时，也按同一缓存和租约生成一次并复用。

AI 文案采用常识整理，机械检查不能保证史实正确；不要将“通过 JSON、姓名和重复校验”称作“事实已核验”。生成提示要求不确定时放弃，不凑数；传说、文学形象须标明。调整线索内容时应增加 `knowledge_revision`，修改生成规则时增加 `CLUE_VERSION`，以使旧缓存和未结束会话失效。

接口只在揭晓后返回人物及完整解释；开局仅返回第一条，后续未解锁内容不会发到浏览器。猜错不扣提示、不自动解锁，重复解锁请求不会跳过两条。签名匿名会话、访问额度及一小时游戏时效沿用当前服务约束。

## 数据库准备命令

先编译 API，再在目标环境应用新增迁移 `database/mysql/004-guess-clues.sql`。该迁移只新增游戏表、难度反馈表及复制身份映射，不修改历史资料。共用目录接入需要此迁移就绪，应先完成游戏表迁移，再发布应用。

只读检查（不会调用 AI，也不会写入）：

```sh
node scripts/prepare-guess-clues.mjs --import games/guess/characters.json --seed games/guess/starter-clues.json
```

按本次任务已授权范围执行游戏数据写入、导入首批题目并准备剩余简单人物：

```sh
node scripts/prepare-guess-clues.mjs --apply --import games/guess/characters.json --seed games/guess/starter-clues.json --require-complete --report /tmp/guess-clues-report.json
```

准备程序先同步完整原题库身份，再逐人核对当前资料指纹与线索版本。报告记录 `ready`、`pending`、`failed` 和 `complete`；`--require-complete` 在仍有缺口时以非零状态退出，不能把只导入题包称为全量准备完成。报告逐人原子保存，重跑从数据库复查并复用已完成结果。

`--person UUID` 或 `--limit N` 可以缩小批量生成范围。`--limit` 只计算实际生成的缺口，已缓存人物不占额度，避免每次续跑都卡在列表第一项。人物导入支持递增 `knowledge_revision`，只提升版本、不回退；更新文案时同步提升人物知识版本和题包指纹，新旧缓存分别留存。导入时校验人物指纹及版本，不能把旧稿直接套到已变更人物。原始模型草稿不等于已校对题目，发布前应抽查实际内容。
