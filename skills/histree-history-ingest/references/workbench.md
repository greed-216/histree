# 连续批次工作台

本流程是新增连续录入的默认方式。命令在仓库根目录运行；批次目录从当前书、当前工作线账本及来源目录确定。已有发布批次仍是不可变档案，修订走发布参考中的独立修订流程。

## 1. 续接并准备一组连续原文

读取本书索引中当前工作线的 `progress`、下一段及待考队列。用下一段分段记录的实际卷/篇章选择范围，不能把最后已发布卷号当作下一卷号。先用 `search-history-library.py` 检索与回查来源，按原文次序选一组连续阅读块；阅读块可能合并标题、评论或拆分自然段，需查看前后上下文。批量按总字数和复杂度调整，不为凑固定段数跨卷或截断需要连续阅读的叙事。

```sh
python3 scripts/history-batch-workbench.py prepare \
  --book '<分段库book_key>' --volume '<卷号候选>' \
  --start '<账本下一段ID>' --count '<阅读块数量>' \
  --batch-key '<新批次稳定key>' --out '<新批次目录>'
```

`prepare` 导出逐字 `source.txt`、`paragraph.json`、聚合 manifest、`packet.json` 和 `curation.json` 骨架，并提供前后上下文与本地人物候选。输出目录必须是新目录。不得仅凭候选姓名自动复用或合并人物。

当前准备器按目录中的 `volume_candidate` 选择范围，按已归档 Git 文本核验底本；整卷审计当前要求该卷使用同一有效TXT且正文连续。来源没有可用卷号、分段结构不满足这些要求、需要跨书补证或专题时，先适配工具并验证；不把未支持的格式假造为普通事件。旧兼容批次的段落ID不改成分段库ID。

## 2. 一次填写史实草稿

`curation.json` 的机械装配字段由工具处理，录入者集中填写史实与依据：

| 字段 | 填写要求 |
| --- | --- |
| `batch_key`、`claim_namespace` | 新批次分别使用本批稳定key作为名称和引用命名空间；跨批同一主体的引用不能复用旧claim key |
| `reused_keys` | 明确复用的已有主体key；保留已有字段，新增出处写独立依据，不覆盖已有生平 |
| `items[].group` | `people`、`events`、`person_events`、`person_relationships` |
| `items[].row` | 遵循[批次字段](../../../docs/DATA_PREPARATION.md)；新主体使用稳定key，所有日期和地点基于证据填写 |
| `items[].evidence[]` | 每处含 `paragraph_id`、`field`、`text`、`quote`、`note`、`time_context`；可用多处引文共同支持一个主体 |
| `paragraph_reviews[]` | 按选定段落顺序逐条记录 `paragraph_id`、`status`、`note`、`observations`；没有新事件也要写处理理由，并保留下面的人物关系对照 |

`quote` 从快照逐字取用，跨行保留原换行，不直接复制阅读块合并排版。`field` 指向row已有字段，`text` 写读者能理解的白话陈述；年份说明写“公元前……年”，不显示内部负整数。`time_context` 按本条证据写纪年或追叙语境，不能给整批统一套年份；当年记事不得误用“确年未载”的默认追叙说明。

分段库若沿用了同卷前一传的标题，先对读卷题和本传正文，再在 `sources/manifest.json` 对应项填写 `reviewed_citation` 与 `citation_review_note`。校订引文须保留原书名、`卷{volume_candidate}` 和完整段落ID；仅校订展示定位，不改原文快照、`paragraph.json` 或字符位置。

逐块区分行动、计划、当事人说法、史论与未具名者；同场出现不推成盟友。关系方向、异体字、别名、同名不同人及既有合并修订按史料校核参考核对。出现同名候选时，`identity_note` 记录具体身份区别或复用依据；不会因此绕过线上身份守卫。

审阅状态只用 `reviewed` 或 `pending_textual_review`。`observations` 保存史论处理、无新增理由、原文疑字、未解决身份与暂不结构化的材料，不把所有原文都转成事件，也不跳过原文。已知有事实理解问题时，先改好或隔离，再准备发布；不能仅将状态改成已审。

每段增加 `relationship_audit` 对照原文明示的亲属、师生、共同学习、宾客、门人、任职及交往。每个明确候选保存原文 `quote`、端点与关系key、处理 `decision` 和理由：新增并配独立claim、复用已发布关系、身份/异说待考、或仅保留事件而不建立长期连接。没有明确关系的段落也在 `observations` 说明。工作台会把额外审阅字段保留到段落账本，但不会自动判断史实或保证候选提取完整。

将人物简介和事件中已写出的关系反查到此对照；先核线上既有端点、方向和关系类型，避免重复建边。共同学习未载教师时只保存原文支持的含义，不补同师或师兄师弟；荐举、愿为弟子、一次进言、战前自称友好不能直接变成已任职、已授业或终身友谊。发布补漏时分别统计各卷本轮新增、此前补录和复用，注明待考；整卷来源覆盖与亲属数量不能替代关系审计。

## 3. 批量生成并集中校核

```sh
python3 scripts/history-batch-workbench.py build '<批次目录>'
```

生成标准批次、coverage、逐段账本、复用清单、校验报告和 `review.html`。工具检查连续范围、快照哈希、逐字引文、主体引用、身份候选和逐段审阅；失败不会替换此前生成的批次。已有 `publication.json` 时禁止重建。

阅读对照页，逐条确认主体、动作、计划与结果、时间、关系方向、引文支持范围和白话表述。首次整理中完成这次校核，不增加每批固定的第二轮文案审查或用户逐行确认。对照页用于审阅，不是已上线证明；工具不能自动完成史实判断。已有 `publication.json` 或 MySQL 的 `publication-mysql.json` 时，批次及出处绑定均不可重建。

## 4. 卷末检查完整覆盖

将本卷待审计的批次作为同一目录下有序的 `part-*`，不要混入原草稿与正式版本两套重复数据，然后运行：

```sh
python3 scripts/history-batch-workbench.py audit '<本卷批次集合目录>'
```

检查分段列表、来源字符区间与整卷一致，以及跨批key冲突、复用对象一致和待考项。句读分段若跳过纯空白，审计须逐段比对底本并将空白区间、原字节哈希记入 `source_whitespace_gaps`；正文缺漏或重叠仍拒绝通过，不改原快照或定位。只对已达到卷末的集合运行；未读完的卷不凑齐审计。当前命令审计本地草稿，正式发布前运行并留存结果；发布后结合本次后端的 `publication-mysql.json`（旧库为 `publication.json`）最终哈希和匿名读回更新发布审计，不重建已发布批次。

原文全部处理、所有潜在事实提取完、所有待考解决、事实公开核验是不同结论。整卷覆盖通过只能证明原文区间完整；存在暂缓项时保留队列，不标全卷完成。

## 5. 转入发布

没有待考隔离需求且批次未发布时，可直接准备该批；需要保留完整试点或隔离疑问时，将审阅后的可发布版本置于同一工作线的独立发布目录，保留原稿、主体key及 `deferred-items.json`。只隔离有问题的节点、连接或断言，不为了发布而删掉原文段落的覆盖记录。

按[发布参考](publication.md)归档新快照，再用 `link-sources` 绑定归档提交。归档过程不把其他工作线或本地未授权提交一并推送。之后重新 `build`、准备导入、只读预检；已授权则发布并逐表匿名读回。

最后检查实际网站的首、中、末代表条目，确认正文、年份或时间不详、人物关联、可展开原文和固定出处可见。已发布内容若需改说明，单独保存修订，做旧值守卫和匿名读回，不改原发布批次。更新当前工作线与本书索引，交接下一段及未解决项。

工作台或发布器发生代码变更时，运行相应测试；常规资料批次运行生成器与内容验证即可，不把全部工具测试作为每批固定开销。卷一试点及实测记录见[工作台说明](../../../docs/HISTORY_BATCH_WORKBENCH.md)，示例数据和历史速度不作为后续录入保证。
