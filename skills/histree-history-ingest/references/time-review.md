# 时间校核

本纪、列传、志、表都可能提供可换算的时间。先判断时间属于哪件事，再换算；不因纪传体就统一置空，也不因同段有年标题就给所有追叙套年。

## 本轮整理应完成的判断

- 保留原纪年、君主/政权或年号。对省略的主语、承接的年次与月份，回查具体上下文段落；事件段和纪年锚点各保留定位。
- 查所用底本的年表或必要补证，核对元年、前后元和重起纪年、同名君主、即位当年与次年改元。表中跨行/合并单元格、空列及列位置变化须人工核对；现代编辑附加的公元对照列标明性质，不冒充古人原话。
- 元年锚点确认后，确定性计算在位年对应的公元年份；不凭模型常识补元年。无0年，跨公元前后时用连续序数算差；原干支、月日保留，另行完成历法换算前不宣称已换算公历日期。十月岁首、闰月及年界不能简单套用公历一月至十二月。
- 检查“初”“明年”“后数年”“时年”“在位若干年”：分别可能是追叙、相对时间、年龄、时长。不能把年龄倒算出的单一生年、在位时长或卷的上下限当作确切事件日期。
- 明确单一发生年写事件年份；真实持续过程才使用起止年。只能约束发生范围的，用年代侧表及精度，不把上下界当持续时长。仅知先后或时代也要保存明确结论和依据。
- 多年多次行动不能给一个“代表年”。拆为可独立核年的事件，或保留总述并把各阶段及各自时间明确写出；后者不冒充单年事件。跨书同一主体仍复用稳定ID，不为了日期不同另建同一事件；异说用独立声明/年代记录保存。
- 复用有年份的旧对象，也检查当前来源的原纪年。相符、仅补细节、无法独立换算和相冲突分别记明；有冲突不静默覆盖旧值。人物生卒与关系时间仅在本轮明确依据支持时整理，不由参与事件自动倒推。

## 逐事件审计与发布

整理草稿时在 `curation.json` 每个事件 item 的 `temporal_review` 中同时填写 `decision`、`reason`、`anchor_note`；`decision` 为 `exact`、`range`、`relative`、`era`、`unknown`、`multiple`、`inherited` 或 `conflicting`。`exact` 同时记录 `year`，事件字段和日期声明必须一起准备。`anchor_note` 说明所用君主、纪年锚点、具体出处及换算/保留理由；不适用换算时解释为什么。

工作台 build 后运行 `python3 scripts/validate-history-time.py <批次>/content-batch.json --from-curation <批次>/curation.json`，从已写的判断生成绑定本批哈希的 `time-review.json` 并验证。默认使用事件第一处引文及其来源；时间依据在另一段时，显式提供正确的 `source_keys` 与逐字 `quote`。没有统一草稿的旧格式新批次，按同一格式直接准备审计：`format_version: 1`、`batch_sha256`、`events`；每项另含稳定 `key`、`source_keys` 与 `quote`。

审计覆盖本批每个事件，来源为本批已核快照。能确定的日期不能只写“待核”；不能确定的须说明已核范围与具体障碍。结构验证只能检查覆盖、引用和字段一致性，不能证明史实准确。新批次发布器会检查时间审计；已有已核验发布档案保持兼容，不重建原批次。

新增批次依既有工作台、归档、MySQL发布与独立进度流程执行。修订旧数据另建带旧值守卫的 `content/revisions/`，保护原批次、原文和旧出处。补查年表不推进被查卷的连续游标。

公开后至少核对：明确日期实际写入且匿名可见；范围/时代保留精度；异说与待考未丢失；有确年的事件进入相应年份画卷，未知年份没有被显示成确年。不得仅凭条目页能打开就宣称年代验收完成。

实际持续过程用 `decision: range` 时另填 `interval_kind: duration`、`start_year`、`end_year`；估计发生范围不能直接写事件持续区间。复用旧对象用 `inherited`，填写 `comparison` 为 `consistent`、`additional_detail`、`unresolved` 或 `conflicting`；后两种保留具体障碍或异说，不把旧日期算成本书新校年。新人物填写生卒年时也必须有对应日期字段的独立证据。
